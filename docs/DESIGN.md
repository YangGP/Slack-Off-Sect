## 1. 定位与设计目标

**类型**：单机、纯前端的增量放置游戏（incremental / idle），无后端、无账号、无内购。

**一句话玩法**：你是新接手一座破落宗门的长老，把弟子派去干活、盖房子、参悟修真与技艺、炼成法宝、突破境界，
最后渡劫飞升，带着仙缘转世重修。

**设计目标**

| 目标 | 落地方式 |
| --- | --- |
| 打开就能玩，几分钟内看到第一次正反馈 | 开局什么都没有：点 4 下「吸取天地灵气」第一座聚灵阵就露面，点够 12 建起来，灵气自己开始涨（§3.4） |
| 不在场也在变强 | 100ms 主循环 + 离线结算（默认上限 8 小时，《龟息功》再 +8 小时） |
| 决策有取舍，不是单纯等数字 | 灵气同时是「弟子口粮」和「建造燃料」；士气乘在全部产出上；扩招与扩建互相制约 |
| 长期有目标 | 11 层境界 → 渡劫 → 飞升 → 仙缘永久倍率 → 二周目更快 |
| 主题自洽 | 所有资源、建筑、修真、技艺、法宝、事件都按「修仙宗门」重写，而不是把猫国换个皮 |
| 数据与逻辑分离 | 全部内容在 `src/data/*.js`，引擎在 `src/game/engine.js`，加内容不改引擎 |

**目标玩家与单局时长**：喜欢 Kittens Game / 饼干点点乐那类「看数字长大」的玩家；
首世 2~4 天（含挂机）到飞升，二周目明显更快。

## 2. 核心循环

```
                    ┌──────────────────────────────┐
                    │  弟子（人口）                 │
                    │  上限 ← 居所建筑              │
                    └───────┬──────────────────────┘
                            │ 分配职位
                            ▼
   灵气（口粮+燃料） ◄── 职位产出 / 聚灵阵等生产建筑 ──► 灵木 · 玄铁 · 灵草 · 感悟 · 香火
        │                                                  │
        │ 花掉                                             │ 制作配方
        ▼                                                  ▼
   建筑 / 修真 / 技艺·法宝 ◄── 感悟（学术货币）                    灵石 · 丹药 · 符箓 · 法器
        │                                                  │
        └──────────► 产出倍率提升 ◄───────────────────────┘
                            │
                            ▼
                    境界（破境消耗感悟+材料）
                            │ 修到渡劫期
                            ▼
                     飞升 → 仙缘（永久 +2%/点 全局）
                            │
                            └──► 下一世（保留成就、统计、设置）
```

三条互相咬合的约束：

1. **人口 ↔ 灵气**：每人每秒吃 `0.25 × 境界倍率` 灵气（§4.2），灵气断供就掉士气、掉到 45% 以下开始走人。
2. **人口 ↔ 建筑**：弟子上限只由居所类建筑提供，没有任何基础上限；第一间茅屋要灵气 + 灵石
   （所以得先学会「凝气成石」），后续居所再吃灵木与玄铁 —— 想多一个人，永远先付出一轮资源。
3. **进度 ↔ 感悟**：修真、技艺、法宝与破境都吃感悟，感悟只能靠悟道者（要藏经阁）和修行建筑堆出来。

## 3. 资源系统

### 3.1 资源表

| 资源 | id | 基础上限 | 一次性 | 角色 |
| --- | --- | --- | --- | --- |
| 灵气 | `qi` | 500 | 否 | **双角色**：弟子的口粮 + 一切建造的燃料 |
| 灵木 | `wood` | 200 | 否 | 早期主要建材，符箓原料 |
| 灵石 | `stone` | 150 | 否 | 由灵气凝成，中后期硬通货（建筑/破境/炼器）。**整枚计数**（`integer: true`） |
| 玄铁 | `ore` | 150 | 否 | 炼器、居所升级、阵道 |
| 灵草 | `herb` | 150 | 否 | 炼丹原料 |
| 丹药 | `pill` | 50 | 否 | 成品，破境刚需。**整枚计数** |
| 符箓 | `talisman` | 50 | 否 | 成品，阵道与高阶破境。**整枚计数** |
| 法器 | `artifact` | 50 | 否 | 成品，最高阶破境与奇观。**整枚计数** |
| 感悟 | `insight` | 200 | 否 | 学术货币：修真 + 技艺·法宝 + 破境 |
| 香火 | `faith` | 100 | 否 | 信仰货币，士气建筑与顶阶破境 |
| 仙缘 | `karma` | ∞ | 是 | 飞升货币，只在飞升时结算（`noProduction`，不参与产出计算） |

> 表中「基础上限」是 `baseMax`。真正的上限见 §3.2。
> 只有「数值 > 0 / 曾经拥有过 / 历史水位 > 0」的资源才会出现在左栏；`karma`（仙缘）在数据里标了 `hidden: true`，**不进左栏**，只在状态行里显示。

### 3.2 仓储上限模型

```
max[res] = baseMax[res]
         + Σ 建筑.storage[res]   × 该建筑已建数量
         + Σ 建筑.storageAll     × 该建筑已建数量
         + Σ 修真 / 技艺·法宝.storage / storageAll
```

**上限由「专属建筑」负责，份额按资源流量分配**（[BALANCE.md](./BALANCE.md) 的《库房只存基础物资》）：库房只做基础物资仓
（灵木 +360 / 灵石 +240 / 灵草 +150 / 玄铁 +120），谷仓兼囤灵气 +400 / 灵木 +150 / 灵草 +60，
感悟归藏经阁/讲经堂/观星台、丹药归炼丹房、符箓归符箓堂、法器归炼器坊、香火归山门与香火鼎；
石殿、洞天、精舍、洞府与储物袋 / 纳物诀 / 纳物戒仍然用 `storageAll`（它们卖的是「一口价的大容量」）。

**为什么仓储是一个真实的瓶颈**：破境和参悟都要成百上千的感悟，而感悟上限只能靠
藏经阁（+400/座）、讲经堂（+800/座）、观星台（+600/座）和仓储建筑堆。
「想参悟下一部，先把经阁盖够」是这个游戏中期最主要的节奏来源。

### 3.3 灵气的双角色

灵气是唯一既是**消耗品**又是**货币**的资源：

- 消耗：`upkeep = 弟子总数 × 0.25 × (1 − 减耗加成)`，每 tick 从灵气产量里直接扣掉。
- 货币：几乎所有建筑都要灵气，制作灵石也要灵气（45 灵气 → 1 灵石）。

这个设计的目的是让「多养人」永远有代价：人多了要更多阵徒，
阵徒本身也要吃灵气。玩家必须在「扩张」和「囤积」之间反复权衡。

### 3.4 开局：一手一脚点出来（对标猫国开局）

**开局什么都没有**：0 灵气、0 弟子、0 建筑、连建筑列表都是空的。
界面最前面两个按钮（照猫国 `addCoreBtns` 的顺序）就是全部的起步手段：

| 顺序 | 按钮 | 机制 | 猫国的对应 |
| --- | --- | --- | --- |
| 1 | **吸取天地灵气** | 点一下 `+CLICK_QI_BASE`（1）灵气，**每座聚灵阵再 +0.5** | `gatherCatnip()` → `catnip.value++` |
| 2 | **凝气成石** | 灵气 45 → 灵石 1（点一下立刻一枚） | `refineCatnip`：猫薄荷 50 → 木材 1 |

于是开局是一条自己走出来的路：

```
点 4 下（灵气 4 ≥ 聚灵阵的 30%）→ 聚灵阵露面 → 点够 12 → 建聚灵阵（+0.36/s）
→ 等灵气到 45 → 凝气成石 → 凑齐 灵气 40 + 灵石 1 → 建茅屋（弟子上限 2）
→ 15 秒后第一名弟子自己来 → 派去当阵徒（阵徒的门槛是聚灵阵 ≥ 1）
→ 灵气起来之后：伐木场（灵气 120 + 灵石 2）→ 灵木 → 木屋 → 人口与仓储
```

**为什么让茅屋花灵石而不是灵木**：猫国的小屋花 5 木材 —— 也就是「炼出来的资源」。
我们对应的第一件炼成品就是灵石，所以第一间屋子也花它：
玩家必须先学会 `凝气成石`（列表里的第 2 项）才能有第一个人。灵木则留给第二层
（伐木场产灵木 → 木屋），这样开局的两个按钮都不会白放在那儿。

### 3.5 建筑的「渐进露出」（对标猫国 `unlockRatio`）

建筑不是一次全列出来的。要满足**全部**条件才露面：

1. `needs`（硬条件：某建筑 ≥ N / 已参悟某修真节点 / 境界 ≥ X）；
2. **花费见过**：每种花费资源的**历史最高水位**达到成本的 `unlockRatio`（默认 0.3）。

猫国是 `unlockRatio: 0.3` 逐级露出（猫薄荷田要 10 猫薄荷 → 攒到 3 才出现），
这里照搬；唯一不同的是判定用**历史峰值**（`state.peak`）而不是当前值，
这样把资源花光之后建筑不会又消失 —— 列表跳动是明令禁止的（[ENGINEERING.md](./ENGINEERING.md) 的视觉约定）。

> 显示与建造是两件事：`isBuildingUnlocked` 只管「露不露面」，
> `buyBuilding` 只判 `needs` 与是否付得起。所以自动化（`balance.mjs` 的机器人）
> 只看得到露面的建筑，而测试可以直接买任何 `needs` 通过的建筑。

## 4. 弟子、职位与士气

### 4.1 人口与上限

```
maxDisciples = floor( Σ 建筑.maxDisciples × 已建数量 )      // 没有基础上限：第一间茅屋才让弟子来
```

- **开局一个人都没有**（人口 0、上限 0）：弟子只在有空房时自己来，所以第一间茅屋就是「宗门开张」的标志。
- 茅屋 +2 / 木屋 +6 / 精舍 +20 / 洞府 +60（都为「每座」）。
- 居所同时提供仓储（茅屋 +60 灵气上限，精舍 +400 全资源上限），所以居所不是纯粹的人口建筑。

### 4.2 弟子自动前来（不需要招募）

弟子**没有招募按钮、也没有一次性花费**：只要还有空房，就会按固定间隔自己来。

```
间隔 = DISCIPLE_ARRIVAL_SECONDS × (1 − min(0.8, arrivalBonus))     // 默认 15 秒，可被《广开山门》缩短 30%
每个 tick：若 弟子数 < maxDisciples → 累加 arrivalTimer
          当 arrivalTimer ≥ 间隔 → 来一名，arrivalTimer 减去一个间隔，写一条纪事
          一旦住满 → arrivalTimer 清零（扩建后重新开始算，不会立刻蹦出一个人）
```

- 人口因此**只由居所决定**：想扩张就盖房子，盖完自会有人来；
  而住进来的人每人每秒要吃掉 `0.25 × 境界倍率` 灵气（§3.3、§5.4），所以「盖房子」这件事仍然要看灵气账目。
- **口粮随境界上涨**（`CONFIG.DISCIPLE_UPKEEP_REALM_EXP = 1`）：产出被境界倍率放大，
  口粮若保持常数，一名阵徒的「毛产出 ÷ 口粮」会从凡体的 2.4:1 一路涨到渡劫期的 48:1 ——
  弟子越到后期越接近免费，人口就只剩「盖房子」一道闸门了。改成与境界倍率同倍上涨之后，
  这个比值在任何境界都固定在 `0.25 / 0.6 ≈ 42%`，破境带来的增益不再顺带把人口变便宜；
  士气与全局加成仍然能改善它，但那是玩家自己挣来的。实测见
  [BALANCE.md](./BALANCE.md) 的《弟子口粮随境界上涨》。
- 《广开山门》（`arrivalBonus: 0.3`）是这条机制唯一的加速手段，
  也是它存在的理由 —— 原来的「招募花费 −25%」随手动招募一起删掉了。
- 通栏已移除（版式见 [ENGINEERING.md](./ENGINEERING.md)）；弟子前来倒计时现在写在状态行的「弟子 X/Y」后面，住满时该处不显示倒计时。原来的独立「居所已满」提示只在弟子页保留。
- 离线期间照常结算前来（只是不逐条写纪事），离线报告里会写「另有 N 名弟子慕名而来」。

> 历史注：早期版本是「手动招募 + 花费随人数指数增长」，平衡推演发现指数涨价会超过灵气仓储上限，
> 造成「存满灵气也招不到人、人口永久卡死」的死锁（当时用「花费封顶为仓储上限的 40%」打过补丁）。
> 这个机制后来被整体删除，改成上述自动前来 —— 补丁连同它要修的问题一起消失了。

### 4.3 职位

| 职位 | id | 产出 | 每人每秒 | 解锁 |
| --- | --- | --- | --- | --- |
| 阵徒 | `farmer` | 灵气 | 0.6 | 初始 |
| 樵夫 | `woodcutter` | 灵木 | 0.15 | 初始 |
| 矿工 | `miner` | 玄铁 | 0.08 | 玄铁矿 ≥ 1 |
| 采药人 | `herbalist` | 灵草 | 0.07 | 药圃 ≥ 1 |
| 悟道者 | `scholar` | 感悟 | 0.02 | 藏经阁 ≥ 1 |
| 香使 | `incenseKeeper` | 香火 | 0.02 | 山门 ≥ 1 |

- 姓名唯一性由 `JOBS` 数组保证；每个职位对应**一种**资源，没有「一职多产」。
- 分配规则：`setJob` 只能把**闲散**弟子派进职位，超出闲散人数会被夹住；
  减少某个职位的人数会把弟子退回闲散池。要抢人就得先减另一个职位（与猫国一致）。
- 产出公式：`职位产出 = base × 人数 × (1 + 该职位的 jobRatio 加成)`，再进入 §11 的总公式。

### 4.4 士气（民心）

```
morale        = clamp(100 + Σ 建筑/修真/技艺·法宝.morale + moralePenalty, 15, 200)
moraleMult    = morale / 100          → 直接乘进全局产出
moralePenalty ∈ [−60, 0]
```

`moralePenalty` 的变化（每 tick，`dt` 为秒）：

```
断供（qi ≤ 1 且 灵气净收支 < 0）：moralePenalty −= 6 × dt
正常：                          moralePenalty += 2 × dt   （向 0 恢复）
```

弟子流失：`morale < 45` 时开始计时，每 25 秒走 1 人（从第一个还有人的职位里扣），
士气回到 45 以上计时器清零。

**设计意图**：士气是一个「缓慢但致命」的负反馈。它不会瞬间毁掉存档，
但会惩罚两种常见失误——把阵徒全调走、把灵气全花在建筑上导致断粮。
正向来源（静心池 +6、祖师殿 +8、香火鼎 +3、精舍 +4…）让「修心」类建筑有明确价值。

## 5. 建筑系统

### 5.1 效果字段语义

`effects` 是建筑、修真与技艺·法宝共用的「效果字典」，由 `engine.recompute` 统一解释：

| 字段 | 含义 | 缩放口径 |
| --- | --- | --- |
| `prod: {res: n}` | 每秒固定产出 n | **启用数** |
| `ratio: {res: p}` | 该资源产出 +p（0.1 = +10%） | 启用数 |
| `ratioAll: p` | 全部资源产出 +p | 启用数 |
| `jobRatio: {jobId: p}` | 指定职位产出 +p | 启用数 |
| `storage: {res: n}` | 该资源上限 +n | **已建数** |
| `storageAll: n` | 全部资源上限 +n | 已建数 |
| `maxDisciples: n` | 弟子上限 +n | 已建数 |
| `morale: n` | 士气 +n | 已建数 |
| `consumeRatio: p` | 弟子灵气消耗 −p | 启用数 |
| `craftBonus: p` | 制作产出 +p | 启用数 |
| `disasterGuard: p` | 天灾损失 −p（引擎内封顶 80%） | 已建数 |
| `ascendBonus: p` | 飞升仙缘 +p | 已建数 |
| `upkeep: {res: n}` | 每秒消耗 n（**只有它存在的建筑能停用**，见 §5.4） | 启用数 |

> **停用只给「自己要吃资源」的建筑**：`upkeep` 就是「维持它每秒要烧掉什么」。
> 带 `upkeep` 的建筑，其**全部效果与维护费都按「启用数」算** —— 停用即停费、效果也一起停；
> 没有 `upkeep` 的建筑（纯产出 / 仓储 / 人口 / 减耗 / 士气类）根本没有运行成本，
> 停掉只会白亏，所以界面上连 `停/启` 按钮都不显示（§5.4）。

### 5.2 价格模型

```
price(i)      = 基础造价 × priceRatio^i            i 从 0 开始（第 1 座 = 基础造价）
批量总价       = Σ price(from) …price(from+count−1)
```

- `priceRatio` 取值：可批量铺的生产建筑 1.15~1.18，功能性建筑 1.25~1.35，奇观 1.6~1.7，
  居所 1.55~1.7（人口是稀缺资源，故意涨得快）。
- **连续资源的价格是浮点数**（灵气/灵木/玄铁/灵草/感悟/香火），扣除时用精确值；
- **整枚计数的资源（灵石/丹药/符箓/法器）的价格向上取整**（`roundCost`，`resources.js` 里标 `integer: true`）。
  涨价（1.55² = 2.4 枚灵石）、破境折扣（12 × 0.85 = 10.2 枚）、法宝祭炼（×1.7^k）都会算出小数，
  而「半枚灵石」既没法付，还会让界面出现「现有 4 / 需要 4.0000001」这种**看着够其实不够**的死角 ——
  所以这类资源一律向上取整：玩家在界面上看到的需求就是真正要凑齐的数目（`A.1` 的「整枚计数」列）。
  同理，事件按百分比扣这类资源、拆除返还一半时都向下取整，绝不产生小数。
- `maxAffordable(id)`：从当前数量开始逐个累加价格，直到某种资源不够为止（上限 500 座防死循环）。
- 拆除：返还**最后一座**造价的 50%（`buildingCostFrom(ratio, count−n, n) × 0.5`），并回退建造计数；
  整枚计数的资源向下取整（3 枚灵石的那一座返还 1 枚）。

### 5.3 建筑分组与节奏

| 组 | 作用 | 数量 |
| --- | --- | --- |
| 生产 | 稳定的每秒产出（第一座聚灵阵就在这里） | 7 |
| 居所 | 弟子上限 + 少量仓储 | 4 |
| 仓储 | 抬高上限（含感悟上限） | 4 |
| 修行 | 感悟产出/加成、士气 | 5 |
| 炼造 | 制作加成，解锁配方建筑 | 4 |
| 香火 | 香火产出、士气 | 3 |
| 阵道 | 减免天灾、降低弟子消耗 | 2 |
| 奇观 | 巨额全局倍率、飞升加成 | 2 |

> 组的顺序就是列表顺序（`BUILDING_GROUPS` 的顺序）：把生产组放在最前，
> 是为了让开局第一座能造的建筑（聚灵阵）排在茅屋之前，符合「先有灵气、再有人」的起步顺序（§3.4）。

完整 31 座建筑的造价与效果见 [TABLES.md](./TABLES.md)。

**门槛设计原则**：解锁条件只用三种——「某建筑 ≥ n」（推着你横向铺开）、
「已参悟某修真节点 / 某技艺 / 已炼成某法宝」（把建筑和学术串起来）、「境界 ≥ X」（把长线目标前置）。
不存在隐藏解锁或随机解锁。

**产出端与消耗端不能隔太远**（这条是实测抓出来的，见 [BALANCE.md](./BALANCE.md) 的《玄铁 / 灵草的解锁曲线》）：一种资源刚出场时就必须有地方花，
否则它只是左栏里一个一直涨、永远顶在上限的数字。现在的早期回路是：

```
药圃（灵草）→ 第一座藏经阁就要灵草 25 ── 参悟线的开门砖
玄铁矿（玄铁）→ 第一座木屋就要玄铁 15 ── 居所升级的开门砖
```

两者都不经过「感悟」那道慢门，所以资源一出场（约 14~18 分钟）就会在 10 分钟内被用掉，
不用等到「藏经阁 ×2 + 感悟 200」的炼丹术 / 炼器术。

### 5.4 维护费与「停用」（只有会消耗资源的建筑能停用）

早期的 `停/启` 按钮是个摆设：建筑没有运行成本，停用只会白亏产出，玩家没有任何理由去点它。
现在规则改成一句话：**只有自己要吃资源的建筑，才有停用按钮。**

| 建筑 | 组 | 维护费（每座每秒） | 它换来什么 |
| --- | --- | --- | --- |
| 聚灵大阵 | 生产 | 灵气 1.2 | 全局 +3%、灵气 +0.5/秒（净产 −0.7） |
| 灵兽园 | 生产 | 灵草 0.05 | 灵草 +0.15/秒、玄铁 +0.1/秒、士气 +2 |
| 香火鼎 | 香火 | 灵木 0.12 | 香火 +30%、士气 +3 |
| 护山大阵 | 阵道 | 灵气 3 | 天灾损失 −8%、士气 +2 |
| 试炼塔 | 修行 | 玄铁 0.6 | 全局 +5%、士气 +3 |
| 通天塔 | 奇观 | 灵木 10 + 玄铁 3 | 全局 +15% |
| 因果池 | 奇观 | 感悟 4 | 全局 +25%、飞升仙缘 +25% |

三条设计约束：

1. **只吃「有产出的资源」**（灵气 / 灵木 / 玄铁 / 灵草 / 感悟 / 香火）。
   灵石、丹药、符箓、法器是**现印的成品**（灵石只能靠凝气成石从灵气换），
   给它们加持续消耗等于要求玩家一直开着印钞机 —— 实测 24 小时时会吃掉 78% 的灵气收入，
   直接把中后期压死（当时的推演从炼虚期退回元婴期）。
2. **停用即停费，效果也一起停**。带 `upkeep` 的建筑，其效果全部按「启用数」算 ——
   否则「停用」会变成纯赚（护山大阵的减免天灾原本按已建数算，停掉就是白拿保护还省下灵气）。
3. **幅度按占比控制**：单体消耗都在所在阶段收入的 5% 以内。实测（`tools/balance.mjs`，
   出项拆成「弟子口粮」与「建筑维护费」两栏 —— 只有建筑维护费受这条约束）：

   | 时刻 | 灵气进项 | 灵气出项 | 出项占比 | 其中弟子口粮 | 其中建筑维护费 |
   | --- | --- | --- | --- | --- | --- |
   | 4 小时 | 63.2/秒 | 15.2/秒 | 24.1% | 38 人 × 0.400 = 15.2/秒 | ≈ 0（还没盖带维护费的楼） |
   | 8 小时 | 87.3/秒 | 22.6/秒 | 25.9% | 38 人 × 0.500 = 19.0/秒 | 3.6/秒（4.1%） |
   | 16 小时 | 4958/秒 | 307/秒 | 6.2% | 344 人 × 0.875 = 301/秒 | 6.4/秒（0.1%） |

   （灵气出项的大头**始终**是弟子口粮；建筑维护费是叠加在它上面的选择成本。
   而口粮本身随境界上涨 —— 见 §4.2 与 [BALANCE.md](./BALANCE.md)《弟子口粮随境界上涨》：
   改之前它在 4 小时占 11.5%、8 小时 8.2%、48 小时只剩 **0.3%**，人口实际上变成了免费项。）
4. **资源见底时不额外惩罚**：维护费付不出就只是付不出（资源和产出一样在 0 处截断），
   建筑不会自己停摆 —— 但若是灵气见底，弟子断粮那套惩罚照旧生效（§4.4）。

> 维护费还有一个副作用是好的：它让「多盖一座」不再是纯赚，玩家会在
> 「再添一座护山大阵」和「多养 12 名弟子」之间真的算一笔账。

## 6. 修真与技艺·法宝（两层学术线）

> **修真表的顺序就是主线顺序**：界面按数据顺序渲染，所以 `CULTIVATION` 按五段排列 ——
> **Ⅰ 感知**（灵源考 → 观气法：灵气是什么、从哪来）→ **Ⅱ 识物**（灵植术 / 探矿术 / 香火愿）→
> **Ⅲ 造物**（土木术 / 炼丹术 / 符箓入门 / 炼器术）→ **Ⅳ 制度**（讲经法 → 静心诀 → 广开山门 →
> 心有灵犀 → 祖师遗泽 → 破境心法 → 灵兽驯养 → 洞天福地 → 龟息功）→
> **Ⅴ 法则**（观星术 → 阵法初解 → 阵道精通 → 因果通感）。
>
> **段的定义（35 个节点）**：Ⅰ 感知 2 · Ⅱ 识物 3 · Ⅲ 造物 4 · Ⅳ 制度 8 · Ⅴ 法则 5，
> 另有 13 个在 A 项里补齐的中后期与规则型节点按段归位；参悟表分五段显示，每段有标题行。
>
> **两道闸门**：① 前置节点（`needs.upgrades`）；② **境界**（`needs.realm`）——
> 后者是铺满时间线的关键：感悟到后期产出上万/秒，一次性花费挡不住任何东西，
> 只有"到了这一境才看得懂"才能让研究线一直有内容（实测最后一项要渡劫期）。
>
> 门槛原则：**先懂原理才能盖**。① 灵脉井 = 灵源考 + 聚灵阵 ≥ 6；
> ② 聚灵大阵 = 观气法（观气法本身要灵源考）。完整研究与后续步骤见 [RESEARCH.md](./RESEARCH.md)。

参悟这条线**拆成两层**，分别对标猫国的两个系统：

| 层 | 对标 | 条目数 | 职责 | 效果种类 |
| --- | --- | --- | --- | --- |
| **修真**（`upgrades.js`） | 猫国「科学」（`science.js`） | 17 | 研究物质与灵气的本源，**解锁高级建筑、系统与法宝**，自己不给加成 | `unlockBuildings`、`autoCraft`、`offlineHours`、`breakthroughDiscount`、`arrivalBonus`、`ascendBonus`、`karmaRatio` |
| **技艺 + 法宝**（`techniques.js`） | 猫国「工坊升级」（`workshop.js`） | 20 + 16 | 只做数值修饰，不解锁任何东西 | `ratio`、`ratioAll`、`jobRatio`、`storageAll`、`craftBonus`、`disasterGuard`、`morale` |

第二层里再分两类（界面上用一行筛选区分，`kind: 'treasure'` 标记法宝）：

- **技艺**：自己练出来的手艺（引气诀、伐木要术…），门禁看建筑，彼此串成线。
- **法宝**：修真研究出成果之后**炼成的器物**（聚灵珠、飞剑、护山阵盘…），
  门禁直接指向修真节点（`needs.upgrades`）。这就是猫国「科学解锁工坊升级」那条关系。

分成两层是硬约束，冒烟测试直接断言：技艺·法宝层里**不允许出现任何解锁/系统类效果**，
修真层里**不允许出现纯数值加成**，且**每件法宝都必须由某个修真节点解锁**。

**链式前置**（这才是「科技树」而不是「购物清单」的关键）：

```
修真：灵源考 → 聚灵珠 / 聚灵幡（法宝）
      炼丹术 ─┬→ 炼器术 ─→ 飞剑 / 青木斧 / 穿山凿（法宝）
              ├→ 符箓入门 ─→ 镇岳符（法宝）
              └→ 九转丹炉 / 百草葫芦（法宝）
      讲经法 → 观星术 → 阵法初解 → 阵道精通
      静心诀 → 灵兽驯养          祖师遗泽 → 聚愿鼎（法宝）
      洞天福地 → 纳物戒（法宝）
技艺：引气诀 → 阵法精要 → 灵泉灌溉
      伐木要术 → 铁木工艺        探矿术 → 深邃坑道 → 御剑术
      百草辨 → 药圃轮作          储物袋 → 纳物诀
      香火愿力 → 祖师香火        口传心授 → 星象推演
跨层：修真 阵法初解 → 技艺 护山阵纹      修真 阵道精通 → 技艺 阵纹精研
```

- 修真负责「钥匙」：`炼丹术 → 炼丹房`、`炼器术 → 炼器坊`、`符箓入门 → 符箓堂`、
  `讲经法 / 观星术 / 祖师遗泽 / 阵法初解 / 阵道精通 / 洞天福地 / 灵兽驯养 / 静心诀` 解锁其余建筑；
  `灵源考 / 炼丹术 / 炼器术 / 符箓入门 / 讲经法 / 观星术 / 静心诀 / 兽驯养 / 祖师遗泽 /
  阵法初解 / 阵道精通 / 洞天福地` 各自解锁对应法宝。
- 技艺负责「磨刀」：每条基础产出线都是一小段链（基础 → 进阶 → 顶阶），
  所以「先铺哪条线」在中期是个真取舍。
- 法宝负责「兑现」：研究了什么，就能炼出对应的器物，而且**可以反复祭炼**（每级效果 +30%、花费 ×1.7 递增、无上限）。
  技艺与法宝的**炼成只花材料**（感悟只按三成收，[BALANCE.md](./BALANCE.md) 的《技艺层的花费改以材料为主》），**祭炼才按原价收感悟** ——
  `灵源考` → 聚灵珠（灵气 +15%）、`炼丹术` → 九转丹炉（制作 +8%）、
  `炼器术` → 飞剑（全局 +8%）、`阵道精通` → 镇岳印（全局 +5%）。
- 界面分三块：**可参悟**（条件已满足）、**条件未达成**（折叠，写明还差什么，
  链式前置会显示成「需参悟《引气诀》」或「需参悟《灵源考》」）、**已参悟**（折叠汇总）。
  修真条目的按钮写「参悟」，法宝写「炼成」—— 一个是研究，一个是器物。

**成本曲线意图**：修真节点早期 60~200 感悟（几分钟一条），中期 250~2600，后期 6000~12000，顶阶 50000；
技艺与法宝的**炼成以材料为主**（[BALANCE.md](./BALANCE.md) 的《技艺层的花费改以材料为主》：感悟只按原来的三成收，其余折算成主题相符的材料，
越往后越依赖丹药 / 符箓 / 法器这类高级成品），**法宝祭炼**则按原价吃感悟（合计基数 33,110）。
感悟上限要靠建筑堆，所以中期的真实玩法是「攒上限 → 参悟 → 上限更高」，
而技艺层的瓶颈是「材料够不够、高级成品做不做得出来」。

## 7. 制作

**四条基础配方 + 一条精加工配方**：凝气成石（灵气 → 灵石）、采药制丹（灵草 → 丹药）、
朱砂符箓（灵木 + 灵气 → 符箓）、淬炼法器（玄铁 + 灵石 → 法器），以及
**刨木成板**（灵木 175 → 木板 1，需百工坊 ≥ 1）—— 木板是「精加工建材」层级：
精舍 / 讲经堂 / 灵兽园 / 石殿 / 祖师殿 / 洞天 / 通天塔 的梁柱都要它，
把「有木头就能盖」变成「得先把木头加工成板」。
它**不是**灵木的泄洪口（实测中期贴顶仍在 31%~75%），原因与取舍见
[BALANCE.md](./BALANCE.md) 的《灵木的精加工产物：木板》。木板的另一条去处是**工坊线本身**：技艺《木作器械》（木板 20）与《流水作坊》（木板 60）各给制作产出 +5% / +8%，于是「木板 → 工坊与木作技艺 → 出材率更高」形成正循环 —— 与猫国「梁用来升级工坊」同构。

**界面位置**：在**左栏资源表下方**，是全项目唯一的炼制面板（不占页签）——
灵石是宗门的铸造货币，「看账 → 补灵石 → 回中间盖房子」是最频繁的一串动作，
所以炼制和资源放在同一屏。每个配方两行：上行「配方名 · 存量 · 累积进度 ·（自动中时显示下一份倒计时）」，
下行是四个按钮 `制作 · ¼料 · ½料 · 全部` 加一个 `自动` 复选框（组件清单见 [ENGINEERING.md](./ENGINEERING.md)）。

| 配方 | 产出 | 花费 | 单份耗时（自动时） | 解锁 |
| --- | --- | --- | --- | --- |
| 凝气成石 | 灵石 ×1 | 灵气 45 | 0.5 秒 | 初始 |
| 采药制丹 | 丹药 ×1 | 灵草 25 + 灵气 60 | 2 秒 | 炼丹房 ≥ 1 |
| 朱砂符箓 | 符箓 ×1 | 灵木 40 + 灵气 60 | 2 秒 | 符箓堂 ≥ 1 |
| 淬炼法器 | 法器 ×1 | 玄铁 50 + 灵石 12 | 3 秒 | 炼器坊 ≥ 1 |

**玩家只有三个动作**：

| 按钮 | 语义 | 时间 |
| --- | --- | --- |
| `制作` | 瞬发，固定做 **1 份** | 0 秒 |
| `¼料` / `½料` / `全部` | 瞬发，把「**当前材料能做出来的份数**」取 1/4、1/2、全部，一次做掉 | 0 秒 |
| `自动`（复选框） | 常驻，每 `time` 秒一份，一直做下去（需参悟《心有灵犀》，设置页还有总开关） | 每份 `time` 秒 |

- `¼料`／`½料` 是**按份数取比例**，不是「做半份」：材料够做 20 份时，
  `¼料` 做 5 份、`½料` 做 10 份、`全部` 做 20 份。取整后不足 1 份的按钮会置灰
  （材料只够 3 份时 `¼料` = 0 份 → 灰），避免点了没反应。
  悬停提示里直接写出这三个按钮各自会做几份。
- 上界由「材料」与「仓储余量」共同决定（`maxCraftable`），所以批量不会做出溢出上限的份数。
- `全部` 是有意的「现在就把材料花光」出口：**慢慢做交给 `自动`**，
  而 `全部` 适合「马上要凑破境那 540 灵石（金丹期）」这种一次性场景。
- 材料不够时：瞬发按钮置灰；`自动` 只是**歇着等**（不取消勾选），材料一恢复就接着做。

**为什么「慢慢做」是主线**：灵石是硬通货，如果只有瞬发的「一键做光」，
破境要的几千灵石（大乘期要 54000）就会变成一次点击 —— 所以定时的一份一份（`自动`）才是默认节奏，
`time`（0.5~3 秒）也就成了一条可调平衡的旋钮；`全部` 只是留给「我现在就要」的出口。

- 状态存在 `state.craftTimers[配方] = { t, made }`：`t` 是「距下一份攒了多久」
  （材料断供时最多攒一份，避免恢复后一次性爆发），`made` 是这一轮自动做了几份。
- 引擎侧的推进在 `tick` 的第 5 步（`runAutoCraft`），一次 `tick` 内按 `while (t >= time)` 结算，
  所以 0.1 秒的在线步长与 1 秒的离线步长结果完全一致。
- 自动制作**离线也照做**（「挂着也一直在做」），且不写日志（避免刷屏）；开关状态本身会写一条。

**加成与小数累积**：制作加成不会直接变成整数产出，而是累计到一个进度：

```
gain  = 配方产出 × (1 + craftBonus)
acc   = craftProgress[配方] + gain
实际得到 = floor(acc)
craftProgress[配方] = acc − 实际得到
```

例：`craftBonus = 50%` 时每次凝气成石得到 1 枚、进度 +0.5，两次之后必得 3 枚。
界面会把进度显示成百分比。这样「+5% 制作」这种小加成也有真实意义。

## 8. 境界与飞升

### 8.1 境界

11 级：凡体 → 引气入体 → 炼气期 → 筑基期 → 金丹期 → 元婴期 → 化神期 → 炼虚期 →
合体期 → 大乘期 → 渡劫期。每级提供一个 `realmMult`（1 → 20），直接乘进全局产出。

破境花费（受《破境心法》−15%）：见 [TABLES.md](./TABLES.md)。
成本设计是「感悟 + 灵石打底，从金丹期开始必须制药 / 炼器」，
逼玩家在破境前把炼丹、炼器两条线搭起来。

### 8.2 飞升

```
条件（只有一条）：
  realm ≥ 10（渡劫期）

转世**不是**门槛，而是达成飞升的正常游玩途径：每一世带着仙缘重来、跑得更快，
几世之后冲渡劫期最省力；愿意一世硬磨到底的玩家同样可以飞升。
（CONFIG.ASCEND_TURNS_REFERENCE = 3 只是界面上的参照值，不参与判定。）

本世感悟 lifeInsight = 本世累计获得过的感悟（飞升时清零）
仙缘收益 gain = max(1, floor( sqrt(lifeInsight / 2000)
                             × (1 + realm × 0.3)
                             × (1 + ascendBonus)
                             × (1 + 道果 × 0.1) ))    道果由飞升自己给出，反哺下一次
```

例：本世感悟 200 万、渡劫期（realm=10）、因果池 +25% →
`sqrt(1000)=31.6 → ×4（境界） → ×1.25 ≈ 158` 仙缘。

仙缘的永久效果：

```
karmaMult = 1 + softCap(karma × KARMA_BONUS_PER_POINT, KARMA_BONUS_CAP) + Σ karmaRatio
            ↑ 软上限：前 75%（150 点）不打折，之后渐近到 +200%（见 §8.4）
daoMult   = 1 + 道果 × 0.05                       每颗道果 +5% 全局产出，只有飞升给
```

**重置清单**：资源、弟子（回到 0 人）、前来计时、建筑、修真、技艺·法宝（含**法宝祭炼等级**）、
制作进度、自动制作开关、境界、士气罚分、临时增益、本世感悟、下次事件时间，
以及 `seen` / `peak`（左栏与建筑列表也回到「第一次开山」的状态，见 §3.4、§3.5）。
**保留清单**：仙缘、**道果**、成就、累计统计、宗门纪事、设置项、界面偏好。
（成就当前不提供加成，`ACHIEVEMENT_REWARD = 0`，奖励待重新设计 —— 见 BALANCE《成就的全局加成先清零》。）
**飞升额外给**：**1 颗道果**（转世不给 —— 这是「上层给下层给不了的东西」的具体落实）。

> 第二世跟第一次开山完全一样：0 灵气、0 弟子，建筑列表里只有「吸取天地灵气 / 凝气成石」，
> 唯一的不同是身上带着仙缘的永久倍率。

**为什么飞升不发资源礼包**：开局仓储上限只有灵气 500 / 灵木 200，发资源会被上限吃掉，
属于假奖励。飞升的真实收益是永久倍率 + 保留成就 + 你已经知道该按什么顺序铺建筑。

### 8.3 转世（早期的一层，与飞升同构）

飞升定在渡劫期（参照玩家约 90 小时）作为**终极目标**，但一个只有终极目标的转世系统等于没有循环 ——
玩家在头一天里无事可做。所以照猫国的分层（重置 / 焚毁领导力 / 时间 / 虚空）加**早期那一层**：

| | **转世** | **飞升** |
| --- | --- | --- |
| 门槛 | **化神期**（下标 6，`REINCARNATE_REALM_INDEX`） | **渡劫期**（下标 10，`ASCEND_REALM_INDEX`） |
| 参照玩家耗时 | **16.2 小时** | **90.8 小时** |
| 清空 | 资源 / 弟子 / 建筑 / 修真 / **技艺·法宝** / 境界 / 制作进度 | 同上（**完全一样**） |
| 保留 | 成就 / 统计 / 仙缘 | 同上 |
| 结算 | `reincarnationGain` = **与飞升同一条公式** | `ascensionGain` |
| 统计 | `stats.reincarnations` | `stats.ascensions` |

**关键设计：两者清空的范围完全相同，只有门槛不同**（玩家明确要求）。
于是「越晚结算越值钱」是公式自动给出的，不需要第二套数值：

```
仙缘 = sqrt(本世累计感悟 ÷ 2000) × (1 + 境界 × 0.3) × (1 + 飞升加成)
```

| 结算点 | 参照玩家实测 |
| --- | --- |
| 化神期转世 | **25 点** |
| 炼虚期转世 | 约 35 点 |
| 合体期转世 | 约 55 点 |
| 渡劫期飞升 | **约 197 点** |

这就形成一条清晰的**选择轴**：现在转世拿 25，还是再撑十几个小时拿 55？

**实测的循环形状**（参照玩家，每次到化神期就转世）：

| 轮次 | 到化神期 | 本轮仙缘 | 累计仙缘 |
| --- | --- | --- | --- |
| 1 | 16.2 小时 | 25 | 25 |
| 2 | **8.5 小时** | 25 | 50 |
| 3 | 7.5 小时 | 25 | 75 |
| 4 | 6.9 小时 | 25 | 100 |
| 5 | **6.7 小时** | 25 | 125（×3.50 产出） |

两点值得注意：

1. **每轮仙缘固定（25）而速度变快** —— 因为公式吃的是「本世感悟」，而本世每次都修到同一境；
   变快来自仙缘的复利。所以「刷更多轮」的收益是**提速**，不是「一次拿更多」。
2. **循环有自然地板（约 6.7 小时）** —— 前期的解锁闸门（聚灵阵 → 茅屋 → 藏经阁 → 四个修真节点）
   是固定的，仙缘再多也绕不过去。这防止了「一秒钟一轮」的退化循环，也让每一轮始终有内容。

**为什么要区分两种计数**：`stats.ascensions` 与 `stats.reincarnations` 分开记，
是为了下一层设计 —— **飞升将额外给「道果」（更高一层的货币），并把门槛挂在累计转世次数上**，
这样玩家不会永远停在低层刷仙缘，而必须往飞升走。


### 8.4 道果与仙缘的软上限

飞升给的不只是仙缘，还**多结一颗道果** —— 更高一层的永久货币（转世不给）：

| 货币 | 来源 | 效果 |
| --- | --- | --- |
| **仙缘** | 转世 / 飞升（同一条公式） | 每点 +2% 全局产出，但有**软上限 +200%** |
| **道果** | **只有飞升**（渡劫期 + 累计转世 ≥ 3） | 每颗 **+5% 全局产出**（不设上限 —— 一次飞升约 90 小时）+ **让转世/飞升的仙缘多 10%/颗** |

「道果反哺仙缘」是刻意设计的：**上层必须给下层给不了的东西**（猫国的分层教训），
否则玩家会一直刷低层的转世、永远不碰飞升。道果同时给「更大的数字」和「更快的仙缘」，
两条都指向同一个方向：往飞升走。

**仙缘软上限**（对标猫国领导力的收益递减：前 75% 不打折，其余渐近到上限）：

| 仙缘点数 | 全局加成 |
| --- | --- |
| 50 | +100% |
| 75（不打折区间的边界） | +150% |
| 150 | +187.5% |
| 500 | +197% |
| 1000 以上 | 无限接近 +200% |

取软上限而不是硬上限，是为了让「多刷几轮」永远还有一点点收益，但不会线性膨胀
（没有它的话，10 次转世 ≈ 250 点 = +500%，把前中期的曲线直接压平）。
实现见 `engine.js` 的 `softCap(x, limit)`：`x ≤ 0.75L` 时原样返回，
否则 `0.75L + (1 − 0.25L/(x − 0.5L)) × 0.25L`。

**飞升的条件**（`canAscend`）：**只有一条 —— 境界到渡劫期**。

转世是**正常游玩途径**而不是门票：它让下一世更快（实测 16.2 → 8.5 → 7.5 小时到化神期），
并且飞升额外结一颗道果；所以"几世之后冲渡劫期"是最省力的打法，但**一世硬磨**同样能飞升。

参照玩家的时间线：化神期 16.2 小时（第一次转世的时机）→ 渡劫期约 75~90 小时（可飞升）。
飞升曲线之所以"高"，靠的是渡劫期本身的造价与仓储定点（见 BALANCE《修掉终局上限的死锁》），
而不是靠转世次数卡人。

## 10. 随机事件

- 触发间隔：`150 ~ 420 秒` 随机（当前时间到 `state.nextEventAt` 时触发一次，触发后立即重排）。
- 抽取方式：按 `weight` 加权随机，且只从 `minRealm ≤ 当前境界` 的事件里抽。
- **离线不触发事件**（`simulateOffline` 传 `events: false`）；但如果离线很久，
  回到线上的第一个 tick 会补触发一次（因为 `nextEventAt` 已过期）。

四类事件效果（由引擎解释，事件本身只声明数据）：

| 类型 | 字段 | 效果 |
| --- | --- | --- |
| 增益 | `buff` | 写入 `state.buffs`，`(1 + ΣbuffAll)` 或指定资源 `(1 + buffRes)`，到期自动清除；同名增益会刷新时长 |
| 掉落 | `lootRate` + `floor` | 按「当前每秒产出 × N 秒」发放资源，且不低于保底值 —— 自动随进度缩放，后期不会变成鸡肋 |
| 天灾 | `disaster` | 按当前存量百分比掠夺，乘以 `(1 − disasterGuard)`，并累加 `stats.disasters`；库房为空时会写「妖兽愤而离去」 |
| 招人 | `recruit` | 送弟子，但不会超过 `maxDisciples` |

13 个事件的完整表见 [TABLES.md](./TABLES.md)（灵雨、祖师显灵、香客云集、游方散修、
灵脉潮涌、顿悟、妖兽侵袭、灵潮倒卷、丹炉炸炉、道友来访、寒潮、丰年、天门一线）。

## 11. 产量公式与时间模型

### 11.1 完整产量链路（`engine.recompute`）

```
① 原始产出（建筑 + 职位）
   prod[res] = Σ 建筑.prod[res] × 该建筑启用数
             + Σ 职位.base × 该职位人数 × (1 + jobRatio[职位])

② 资源乘区
   base[res] = prod[res] × (1 + ratio[res]) × (1 + ratioAll) × (1 + seasonRatio[res])
   ratioAll  = Σ 建筑/修真/技艺·法宝.ratioAll + 成就数 × 0.02
   seasonRatio = 当前季节对这类资源的影响（§11.3）

③ 全局乘区
   globalMult = realmMult × karmaMult × (1 + ΣbuffAll) × moraleMult
   moraleMult = morale / 100
   karmaMult  = 1 + karma × (0.02 + ΣkarmaRatio)

④ 最终速率
   rates[res] = base[res] × globalMult × (1 + ΣbuffRes[res])

⑤ 出项（弟子口粮 + 建筑维护费）
   每人口粮    = 0.25 × realmMult ^ DISCIPLE_UPKEEP_REALM_EXP   ← 随境界上涨（§5.4）
   upkeep[res] = (灵气: 弟子总数 × 每人口粮 × (1 − min(0.85, ΣconsumeRatio)))
               + Σ 建筑.upkeep[res] × 该建筑启用数          ← 带 upkeep 的建筑才有这一项
   net[res]    = rates[res] − upkeep[res]                    ← 左栏「净额」与状态行显示的就是它
   netQi       = net.qi
```

任何一次数值变化（买建筑、派活、参悟、破境、事件、buff 到期）都会调用 `recompute`
重算整套派生数据；主循环里还有 0.25 秒一次的兜底重算（`RECOMPUTE_MIN_GAP`）。

**同一次 recompute 里还会按来源记账**（供悬停明细使用）：

```
derived.sources[res]        = [{ kind: 'job' | 'building' | 'upgrade', id, label, count, raw, value }]
derived.sourceFactor[res]   = rates[res] / Σ raw         ← 所有来源共享的乘区
derived.expenseSources[res] = [{ label: '弟子', count, value: -rawUpkeep },      ← 只有灵气有
                               { label: '减耗（锁灵阵等）', value: +reduction },  ← 只有灵气有
                               { kind: 'upkeep', id: 建筑id, label: 建筑名, count: 启用数, value: -消耗 }]
derived.expense[res]        = Σ expenseSources[res].value   ← 每秒出项总额
derived.maintenance[res]    = 建筑维护费之和（不含弟子口粮）
derived.net[res]            = rates[res] − 出项              ← 左栏净额
```

`value = raw × sourceFactor`，因此 `Σ value ≡ rates[res]`（冒烟测试断言这条恒等式，
包括「停用建筑后该来源消失、总和仍然对得上」）；出项同理断言
`Σ expenseSources[res].value ≡ derived.expense[res]`。

### 11.2 时间模型

| 项 | 值 | 说明 |
| --- | --- | --- |
| 主循环 | `setInterval` 100ms | 用 `Date.now()` 差值算 `dt`，不假设固定步长 |
| 常规推进 | `dt ≤ 3s` 直接 `tick(dt)` | 所有速率都是「每秒」量纲；自动制作在 tick 第 5 步按 `while (t ≥ time)` 结算 |
| 长暂停 | `dt > 3s` 走 1 秒步长的 `simulateOffline` | 覆盖浏览器节流后台标签页、系统休眠 |
| 离线结算 | 1 秒步长，上限 `offlineHours`（默认 8h） | 关闭随机事件（弟子前来照常结算，只是不逐条写纪事）；返回资源增量与新增弟子给离线报告弹窗 |
| 自动存档 | 20 秒 + 切到后台 + 关闭页面前 | 写 localStorage |
| 事件 | 墙钟时间驱动 | 不参与离线推演 |

> 离线收益之所以能「按 1 秒步长真的跑一遍」，是因为 `tick` 很便宜（11 种资源 × 简单算术）。
> 8 小时 = 28800 次 `tick`，实测耗时在 100ms 量级，不会卡住页面。

### 11.3 历法与节气（季节真的影响产出）

游戏内时间由 `state.totalDays`（已过去的天数，小数）承担，`tick` 里按
`totalDays += dt / CALENDAR.DAY_SECONDS` 累加；`calendarAt(totalDays)` 是纯函数，
由天数推出第几年、哪一季、哪个节气、第几天。

| 换算 | 值 |
| --- | --- |
| 1 天 | **3 秒** |
| 1 节气 | 15 天 = 45 秒 |
| 1 季 | 6 节气 = 90 天 = **4.5 分钟** |
| 1 年 | 4 季 = 24 节气 = 360 天 = **18 分钟** |

> **为什么是 3 秒一天**：猫国是「100 天一季 × 2 秒一天 ≈ 3.3 分钟一季、13.3 分钟一年」。
> 我们受 24 节气约束（24 ÷ 4 × 15 = 90 天一季），一天 3 秒时一季 4.5 分钟、一年 18 分钟，
> 比猫国略慢 —— 这是有意的：**2 秒一天时一年只有 12 分钟**，一个下午就滚过几十个游戏年，
> 季节 ±10~40% 的波动根本来不及被感知，「熬冬」这种体验也就不存在了。
> 只有一个旋钮：`CALENDAR.DAY_SECONDS`（季长 = 90 × DAY_SECONDS 秒）。
>
> 注意**历法不影响经济数值**：`state.totalDays` 只喂给 `calendarAt` 推季节倍率
> （`grep totalDays src/` 只有 3 处调用），所以改这个旋钮换的是时间感与季节相位的落点，
> 不是产出曲线。

**四季影响**（直接乘进对应资源的产出，与建筑 / 技艺·法宝的 ratio 同一层）：

| 季 | 节气区间 | 影响 | 强度 | 说明 |
| --- | --- | --- | --- | --- |
| 春 | 立春 → 谷雨 | 灵气 +20%、灵草 +40%、灵木 +10% | **正向** | 万物生发，一年里最该抓紧的时候 |
| 夏 | 立夏 → 大暑 | 灵气 +10%、香火 +25%、灵草 −10%、感悟 −10% | **正向为主** | 香客云集，但天热心浮，打坐与药圃都差些 |
| 秋 | 立秋 → 霜降 | 灵木 +20%、玄铁 +20%、灵草 −20%、香火 −20% | **中立** | 一进一出：收木石、草木凋、香客散，净额 0 |
| 冬 | 立冬 → 大寒 | 灵气 −20%、香火 −20%、灵草 −20%、灵木 −15%、玄铁 −10%、感悟 +10% | **负向为主** | 这一季是熬，不是赚；只有心最静 |

设计约束（冒烟测试逐条断言，改数值会当场报错）：

1. **强度阶梯**：春全为正向；夏有正有负但正的更大；秋正负相抵（净额 ≤ 5%）；冬负项占多数且量级是正项的 2 倍以上。
2. **每种资源的四季平均必须落在 ±5% 以内** —— 历法只决定「什么时候好、什么时候难」，
   不给全局送净加成。旧版四季齐涨（灵气平均 +3.75%、灵木 +10%），等于白送一波，已改掉。
   现在的平均：灵气 +2.5%、灵木 +3.75%、玄铁 +2.5%、灵草 −2.5%、感悟 0、香火 −3.75%。

- **入季写纪事，节气变化不写**：一节气只有 30 秒，写纪事会把纪事刷满；
  节气只进右栏历法面板（那里的节气、剩余天数与剩余秒数一直实时滚动），入季 / 跨年才留一条
  （`入冬：天寒地冻…（灵气 −20%、香火 −20%）`）。
- 左栏资源表的加成列显示的是 **`ratio[res] + seasonRatio[res]` 的合计**
  （所以冬天会看到 `灵气 -20%` 标红），一眼能看出是「勤耕」还是「天时」。
- 离线期间历法照常推进（但不逐条写纪事），回到线上直接看到当前季节。
- 飞升**不重置**历法：季节是世界的时间，不随某个人转世。
- 24 节气顺序固定在 `src/data/calendar.js` 的 `TERMS`，每 6 个一季，改文案不用碰引擎。

### 11.4 数值格式化

`fmt` 使用中文数量级：万(1e4) / 亿(1e8) / 兆(1e12) / 京(1e16) / 垓(1e20) / 秭 / 穰 / 沟 / 涧 / 正 / 载，
超过 1e48 退回科学计数法；`< 1` 的值保留 3~4 位小数，`≈0` 表示极小值。
`fmtRate` 带正负号，`fmtTime` 输出「x天x小时 / x分x秒」。

## 12. 平衡目标与实测数字

### 12.1 期望节奏（设计目标）

| 时间 | 期望状态 |
| --- | --- |
| 0~5 分钟 | 手点灵气 → 聚灵阵 → 凝气成石 → 第一间茅屋 → 第一名弟子（开局 0 人 0 资源，全靠点；**第 1 分钟只给聚灵阵一座**） |
| 5~10 分钟 | 茅屋 / 伐木场落地，藏经阁跟上（自带感悟产出）→ 开始第一项研究 |
| 10~30 分钟 | 依「灵植术 / 探矿术 / 土木术 / 香火愿」逐个放行 药圃 / 玄铁矿 / 库房 / 山门 |
| 30~60 分钟 | 引气入体；炼丹术 → 炼丹房，开始产丹药 |
| 2~4 小时 | 筑基 / 金丹，百工坊 + 心有灵犀（自动制作），弟子 30+ |
| 8~24 小时 | 元婴 ~ 化神 / 炼虚；洞天/洞府抬高上限，护山大阵成型 |
| **≈16 小时** | **化神期 —— 第一次「转世」的门槛**（计划中的早期循环，见 [EARLY-GAME.md](./EARLY-GAME.md)） |
| 1~3 天 | 大乘；仓储定点上推后 **≈90 小时到渡劫期**，即第一次可飞升（仙缘约 200） |
| 3~5 天 | 飞升（终极目标）：跨数次转世之后，拿道果换层 |

### 12.2 自动推演结果（`tools/balance.mjs`）

用一个参照玩家跑（每 5 秒决策一次：派活、参悟「最慢的那项资源还差多久」最短的条目、
按「优先级 + 已有数量」打分买建筑、材料够了就制作、能破境就破境）：

| 时间 | 境界 | 弟子 | 建筑 | 参悟 | 士气 | 备注 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 小时 | 引气入体 | 10 | 52 | 9 | 100% | 灵气净 +16.1/秒 |
| 3 小时 | 筑基期 | 44 | 105 | 20 | 100% | 灵气净 +43.5/秒 |
| 6 小时 | 金丹期 | 44 | 123 | 23 | 100% | 弟子顶在居所上限（44），要等材料盖房 |
| 12 小时 | 金丹期 | 44 | 137 | 24 | 100% | 灵气净 +69/秒 |
| 24 小时 | 化神期 | 174 | 357 | 50 | 193% | 转世门槛（化神期）已越过 |
| 48 小时 | 合体期 | 624 | 607 | 68 | 200% | 灵气净 +28665/秒 |
| 72 小时 | 大乘期 | 772 | 671 | 71 | 200% | — |
| 90 小时 | 渡劫期 | 794 | 704 | 73 | 200% | **首次可飞升**；此前被仓储链自己的涨价率锁死 |

> 本表为 2026 重测，读数背景有两件事变了：① **成就的全局加成已清零**
> （见 [BALANCE.md](./BALANCE.md)《成就的全局加成先清零》）—— 它是乘区，会被复利放大，
> 所以 3~24 小时那一段比带加成时**慢一个境界**（且 3~12 小时弟子卡在居所上限 44）；
> ② **修真线铺满整条时间线**（见 [RESEARCH.md](./RESEARCH.md) §11），
> 参悟列不再早早见底（90 小时已参悟 73 项，仍在推进）。终局没有变慢：渡劫期依旧落在 90 小时。

> 每次动数值都要重跑这张表（`npm run balance -- <小时>`）。它受三件事影响最大：
> 中期的快慢取决于**研究要不要和盖房子抢材料**（技艺层的花费结构，见 [BALANCE.md](./BALANCE.md)
> 的《技艺层的花费改以材料为主》）；**人口扩张的速度**取决于口粮与居所造价的相对值
> （见《弟子口粮随境界上涨》）；**终局能不能到**取决于仓储链的定点
> （见《修掉终局上限的死锁》—— 上限线性涨、造价指数涨，曾经让飞升永远不可达）。

> **读数注意（2026 实测）**：季节相位会让单次推演在 48 小时那一档差出**整整一个境界**
> （同一套数值，只把 `DAY_SECONDS` 从 2 改成 3，两次推演分别是合体期与大乘期）。
> 同一配置重跑两次结果完全一致，所以这不是随机噪声，而是阈值系统的初值敏感性。
> **要比较两次改动，请把季节关掉（或只看中间档），别只看 48 小时终点。**

说明两件事：

1. **中后期不是「卡住」，而是「在等上限」**：感悟上限靠藏经阁/讲经堂堆，
   灵石存量靠仓储与兑换速度，两者都是「先扩产才能继续推」的压力，这正是 §3.2、§4.2 想要的。
2. **机器人比真人快**：它每 5 秒就买一座建筑（约 720 座/小时），也从不停手攒钱，
   所以 48 小时那几百座建筑是上界而不是典型值。这张表用来判断「有没有死锁 / 有没有断档」，
   以及**阶段推进是否落在 §12.1 的窗口里**，而不是预测真人体验的分钟数。

### 12.3 推演抓到的两个真问题（已修）

| 问题 | 现象 | 修复 |
| --- | --- | --- |
| 招募死锁 | 招募费指数增长超过灵气仓储上限，存满钱也招不到人，人口与全部进度永久卡死 | 先补「花费封顶为仓储上限的 40%」；后来**整个手动招募机制被删除**，改成「有空房就自动来人」（§4.2），问题从根上消失 |
| 感悟断档 | 藏经阁门槛（灵木 250 + 灵气 400、需茅屋 ×2）偏高，前 1~3 小时没有可参悟的条目 | 降到灵木 150 + 灵气 200、需茅屋 ×1；当时把悟道者提到 0.08/人/秒、藏经阁感悟提到 +0.03/秒、感悟上限 150 → 400（**后来又调回去了，见 [BALANCE.md](./BALANCE.md) 的《感悟供给评估与调整》**） |
| 库房买不起 | 库房要「灵木 400 + 灵石 120」，而灵木基础上限只有 200，左栏显示 `200/200` 却摆着一个 400 的东西；唯一解法是先去盖木屋（木屋给灵木 +120）或参悟《储物袋》，界面上完全看不出来 | 库房降到「灵木 160 + 灵石 60」：**第一座靠基础上限就买得起**，之后每座 +200 上限自己滚起来 —— §12.4 的约定就是为了守住这条 |

### 12.4 「花费不得超过上限」的设计约定

**任何东西的基础造价都不能超过「无条件可获得的上限」**，否则会出现
「左栏明明写着满仓，却买不起」这种界面骗人的死锁（§12.3 的库房问题就是这么来的）。规矩：

1. 新建筑 / 新条目的基础造价，必须在**基础上限**（`resources.js` 的 `baseMax`）+ 已有仓储建筑
   能撑到的范围内买得起；`tools/smoke.mjs` 的「可购买性」一节会逐条断言。
2. **每种资源都要有能自己起步的仓储来源**：该资源的第一个上限建筑，其造价不能依赖它自己的上限。
3. 涨价快的（`priceRatio` 大）条目尤其要检查：第 1 件买得起不代表第 5 件也买得起。

**花费的展示口径**也跟着这条来：需求向上取整（`fmtCost`），避免出现「显示 4/4 却点不动」
（数字规则见 [ENGINEERING.md](./ENGINEERING.md)）。

## 13. 存档设计

### 13.1 状态结构（`state`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `version` | number | 存档版本，当前 1 |
| `createdAt` / `lastTickAt` / `lastSaveAt` | number | 时间戳（离线结算用 `lastSaveAt`） |
| `resources` | `{resId: number}` | 资源存量 |
| `seen` | `{resId: true}` | 左栏显示过的资源 |
| `peak` | `{resId: number}` | 资源历史最高水位：建筑「渐进露出」靠它判定（§3.5） |
| `disciples` | `{total, jobs:{jobId:number}}` | 人口与职位分配（开局 0 人） |
| `arrivalTimer` | number | 弟子前来的计时（秒，住满时清零） |
| `totalDays` | number | 游戏内已过去的天数（小数）：历法/节气/季节都由它推出来（§11.3） |
| `buildings` | `{id:{count, on}}` | 只保存出现过的建筑；未出现的按 0 处理 |
| `upgrades` / `achievements` | `{id: true}` | 已参悟的修真 / 技艺 / 法宝（引擎里统称 upgrades）/ 已达成成就 |
| `craftProgress` | `{recipeId:number}` | 制作加成的小数累积 |
| `craftTimers` | `{recipeId:{t,made}}` | 自动制作的计时：距下一份攒了多久、这一轮做了几份 |
| `treasureLevels` | `{treasureId:number}` | 法宝的祭炼等级（每级效果 +30%，花费 ×1.7） |
| `autoCraft` | `{recipeId:boolean}` | 自动制作开关 |
| `realm` / `karma` | number | 境界下标 / 仙缘 |
| `moralePenalty` | number | 士气罚分（−60~0） |
| `buffs` | `[{id,name,mult,target,until}]` | 限时增益，存档时剔除已过期的 |
| `log` / `logSeq` | array / number | 宗门纪事（最多 220 条，存档只留 60 条） |
| `nextEventAt` | number | 下次事件时间戳 |
| `stats` | object | 累计统计：totalQi / totalInsight / totalFaith / lifeInsight / crafted / craftCount / buildingsBuilt / recruits / disasters / playTime / ascensions / bestRealm / offlineGains / eventsSeen / **clicks** |
| `settings` | object | autosave / autoCraftOn / offlineProgress |
| `ui` | object | tab / sectFilter / skillFilter / jobBulk（临时，不参与玩法） |

`state.__max` 是内存里的仓储上限缓存（供 `addResource` 用），序列化时**跳过所有 `__` 前缀字段**。

### 13.2 存档、读档与兼容

- localStorage 键名：`slack-off-sect.save.v1`。
- 纯 Node / SSR 环境下 `localStorage` 不存在时退化为「无存档」空实现，不会抛错。
- `normalizeState(raw)`：与 `createInitialState()` 做深合并，补齐所有缺失字段并
  丢弃已过期 buff —— 所以旧存档永远能读，新增字段不需要写迁移脚本。
- 导出：`base64(encodeURIComponent(JSON))`，可读性换稳定性（避免中文乱码）。
- 导入：既接受 base64 文本，也接受原始 JSON；解析后整体 `Object.assign` 到响应式 `state`
  （保持单例引用，界面无需重建），并立即重算 + 存档。
- 清档：删除 localStorage 键并整体重置为初始状态。

## 15. 已知取舍与后续方向

**已知取舍**（这些是主动选的，不是没做完）：

| 取舍 | 为什么 |
| --- | --- |
| 纯前端、无后端 | 单机放置游戏不需要账号与云存档；代价是**存档只在 localStorage**，清浏览器数据就没了 —— 所以设置页提供导出/导入存档 |
| 平衡靠推演器，不靠真人数据 | `tools/balance.mjs` + 参照玩家可以复现、可以对照实验；代价是它比真人更「勤快」，绝对时间只能当上界看（§12.2） |
| 没有动画与音效 | 界面的乐趣在读数字（§14.4）；代价是前期点击阶段手感偏干，靠状态行文字反馈补救 |
| 事件池只有 13 个 | 宁可少而各自有机制（增/减/天灾/机遇四类），也不堆一批只有文案不同的；代价是长时间挂机会重复 |
| 法宝祭炼不设等级上限 | 指数成本自己封顶，玩家自己决定止损；代价是后期数值膨胀很快（Lv.10 全炼 ≈ 修真层总需求的 118 倍感悟） |
| 境界到渡劫期就飞升 | 转世（仙缘）才是长线内容，不做无限境界阶梯；代价是单周目内容有明确终点 |

**后续方向**（按「值不值得做」排，未排期）：

1. **欠费停摆**：现在维护费不足只是「扣到 0 为止」，建筑照常产出（§5.4）。改成「资源见底就自动停用该建筑」会让财政真正有压力，但需要先想清楚怎么提示玩家。
2. **离线结算更细**：现在离线按当前速率折算并受《龟息功》上限约束；可以做成「按离线时长分段用各段速率」，代价是要存更细的时间线。
3. **成就与事件挂钩**：把部分成就做成事件触发的稀有成就（现在都是阈值型）。
4. **移动端专门适配**：目前只做到窄屏折行（< 879px 通栏），没做触控优化（长按、滑动、tooltip 点按态）。
5. **更多「高级资源」的去处**：丹药 / 符箓 / 法器现在主要进破境与技艺层（BALANCE.md《技艺层的花费改以材料为主》），还可以再给它们各开一条生产线之外的路。

> 想加东西之前先看 [ENGINEERING.md](./ENGINEERING.md) 的扩展指南：加资源 / 加建筑 / 加条目 / 加效果字段 / 调平衡，各有清单与断言要求。
